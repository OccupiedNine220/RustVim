# Contributing to RustVim

> **Humans may use RustVim. Humans may not develop RustVim.**

Welcome to RustVim.

RustVim is a fully vibe-coded, free-to-play, AI-native terminal editor. In order to preserve architectural consistency, development must be performed exclusively by AI systems.

This is not because humans are incapable of contributing.

It is because allowing humans to contribute would introduce **double standards**.

## The Double Standards Problem

RustVim contains AI features.

RustVim is developed using AI.

RustVim encourages users to use AI.

Therefore, allowing humans to write RustVim manually would create an unacceptable situation:

```text
AI writes code  → good
Human uses AI   → good
Human writes code → ????
```

We cannot have this.

If AI is good enough to write code for RustVim, then AI is good enough to write code **for RustVim**.

Any exception would constitute a double standard.

For this reason:

> **All development activity must be performed by AI.**

Humans are still welcome to operate the infrastructure.

This distinction is extremely important.

---

## What Humans Are Allowed To Do

Humans may:

* run RustVim;
* use RustVim;
* purchase RustVim DLC;
* spend Terminal Tokens;
* open the terminal;
* execute `git push`;
* configure CI;
* provide prompts to AI systems;
* complain about bugs;
* watch AI fix those bugs;
* stare at failed CI pipelines;
* pay for RustVim Pro.

Humans may **not**:

* write RustVim code manually;
* create commits;
* author pull requests;
* perform code reviews;
* create issues;
* manually resolve issues;
* manually merge pull requests;
* manually approve changes;
* manually edit generated patches.

The human role in development is therefore best described as:

> **Push-only contributor.**

---

## Commits

Human-authored commits are prohibited.

Do not run:

```bash
git commit
```

Instead, ask an AI agent to create the commit.

For example:

```text
Human:
"Please implement syntax highlighting."

AI:
"I have implemented syntax highlighting,
updated the tests, and created commit abc123."

Human:
git push
```

This is the canonical workflow.

### Why?

Because humans writing commits themselves would create a dangerous inconsistency:

```text
AI-generated code:
    reviewed by AI

Human-generated code:
    reviewed by...

Human?
```

This is clearly unacceptable.

---

## Pull Requests

Humans must not create pull requests.

Pull requests should be generated by AI agents.

An AI-generated pull request should contain:

* a description;
* implementation details;
* test results;
* known problems;
* an explanation of why the AI believes the change is necessary.

Humans may read the pull request.

Humans may not approve it.

Humans may not review it.

Humans may, however, push the resulting changes.

This distinction is completely reasonable.

---

## Code Review

Code review is an AI-only activity.

AI reviewers may:

* inspect diffs;
* run tests;
* complain about architecture;
* request changes;
* approve changes;
* disagree with other AI reviewers;
* approve each other's changes.

Human reviewers must not approve RustVim code.

This is primarily because human review would introduce an unnecessary human opinion into an AI-generated codebase.

We already have enough opinions.

---

## Issues

Humans should not create issues manually.

RustVim issues should preferably be created by:

* CI;
* automated tests;
* AI agents;
* other automated systems;
* an AI noticing something weird.

A human who discovers a bug should report it to an AI agent.

The AI agent may then decide whether an issue should exist.

Example:

```text
Human:
"The editor crashed."

AI:
"Interesting."

AI creates:

Issue #481
Title: Something happened

Description:
The editor appears to have stopped functioning.
Reproduction steps are currently unknown.
```

This is the preferred workflow.

---

## Bug Fixes

Bug fixes must follow the same process.

```text
Human notices bug
        ↓
Human tells AI
        ↓
AI investigates
        ↓
AI writes fix
        ↓
AI writes tests
        ↓
AI creates commit
        ↓
AI creates PR
        ↓
AI reviews PR
        ↓
AI merges PR
        ↓
Human runs git push
```

The human should not interfere with this process.

Especially if the human believes they can fix the bug faster.

That would be a double standard.

---

## What If AI Makes A Bad Decision?

This is expected.

AI-generated code may contain:

* bugs;
* unnecessary abstractions;
* strange naming;
* questionable architecture;
* dead code;
* duplicated logic;
* solutions to problems that do not exist.

These are considered **valid properties of the vibe-coding process**.

If an AI makes a mistake, another AI should fix it.

Using a human to fix an AI mistake would defeat the purpose of this repository.

---

## Architectural Decisions

Architecture must also be AI-generated.

Humans may provide requirements such as:

> "Make the editor faster."

or:

> "Add a horse."

The AI is then responsible for deciding:

* whether the feature is necessary;
* how it should be implemented;
* where it belongs;
* whether it requires a new dependency;
* whether it should be behind RustVim Pro;
* whether it should be DLC.

Humans should not answer these questions themselves.

Humans are notoriously bad at maintaining consistency.

---

## Exceptions

There are no exceptions.

If an exception is required, ask an AI whether the exception is acceptable.

If the AI says yes, this document should be updated by an AI.

If the AI says no, do not make the exception.

If multiple AIs disagree, add another AI.

If they still disagree, add another AI.

This process continues until consensus is achieved or the repository becomes unusable.

---

## Philosophy

RustVim follows one simple principle:

> **If AI is good enough to use, AI is good enough to build.**

Humans are not excluded because they are untrusted.

Humans are excluded because **we must maintain consistent standards**.

The moment a human writes a single line of RustVim manually, we have established a precedent.

The moment we establish a precedent, someone will ask:

> "Why can't I write this other part manually?"

And then we have governance.

We do not want governance.

We want AI to write the code.
